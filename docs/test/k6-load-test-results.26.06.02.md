## 04 — 결제 동시성 테스트

**설정:** `shared-iterations` 실행기, 30 VU × 1회 = 동시 30 요청  
**목표:** 동일 주문에 대한 동시 결제 요청 처리 동작 검증

### 결과

```text
concurrent_successes:  10
concurrent_failures:   20  (레이트리밋 429)
```

| VU 분류 | 건수 | 응답 | 원인 |
|---------|------|------|------|
| 레이트리밋 차단 | 20 | 429 | 동일 사용자 동시 요청 제한 |
| 결제 생성 성공 | **10** | **201** | 레이트리밋 통과 후 PENDING 생성 |

체크 31/31 (100%) 통과 — "로그인 200" ✅, "결제 생성 201 또는 중복차단 4xx" ✅

### 설계 의도 (버그 아님)

`generatePayment()`가 동시 호출 시 PENDING 결제를 여러 건 생성하는 것은 **의도된 동작**이다.
중복 완료 차단은 `confirmPayment()` 단계에서 Order 비관적 락 + `completePayment()`의
상태 전이 검증(`ORDER_CANNOT_COMPLETE_PAYMENT`)으로 보장된다.

> 이전(06-01)에는 이를 버그로 분류했으나, `confirmPayment()` 보호 로직 확인 후 설계 의도로 재분류.
> 상세: [`payment-concurrency-bug.md`](./payment-concurrency-bug.md)

### 06-01 대비 변경 사항

이전 실행에서 `k6-bidder-5@test.com` 로그인 실패 오류가 발생했다.

**원인:** `run.sh all` 실행 시 `k6-buyer@test.com` 회원가입(1건) + 입찰자 5명 회원가입(5건) = IP당 6회로 `signupLimit(5/60s)` 초과 → k6-bidder-5 미생성.

**수정:** `seed-bid-test-data.sql`에 `INSERT IGNORE`로 5명을 SQL에서 직접 생성하도록 변경. `run.sh`의 curl signup 루프 제거.

```sql
INSERT IGNORE INTO users (email, password, nickname, user_role, ...)
VALUES ('k6-bidder-1@test.com', '$2a$10$...', 'k6bidder1', 'USER', ...),
       ...
       ('k6-bidder-5@test.com', '$2a$10$...', 'k6bidder5', 'USER', ...);
```

이번 실행에서 로그인 오류 없이 정상 통과.
