1단계: 도메인 이벤트 발행 → 알림 컨슈머 / 핸들러

각 도메인은 자기 비즈니스 로직만 처리하고, 알림 도메인이 동일한 이벤트(Kafka 토픽 또는 Spring ApplicationEvent)를 독립적으로 구독해 알림을 전담한다.

발행 출처 전달 방식 알림 컨슈머 / 핸들러 NotificationType → 대상자
정산 생성
SettlementCreatedEvent		 인프로세스
AFTER_COMMIT + REQUIRES_NEW		 NotificationSettlementEventHandler SETTLEMENT_CREATED → 판매자
입찰 갱신(낙찰가 갱신)

groupId: refund-notification-group		 NotificationRefundEventConsumer REFUND_REQUESTED → 구매자
REFUND_APPROVED → 구매자 + 판매자
REFUND_REJECTED → 구매자
결제 완료/자동결제 실패/직접결제 실패 Kafka "payment"

경매 활성화/취소/검수/낙찰/즉시구매

(즉시구매) PAYMENT_COMPLETED → 구매자 + 판매자, AUCTION_LOST → 직전 최고 입찰자

관리자 정산 완료
NotificationSendEvent 기존(범위 제외)		 인프로세스
AFTER_COMMIT + REQUIRES_NEW		 NotificationEventHandler SETTLEMENT_COMPLETED → 판매자
이 중 경매(통합)와 주문 승격은 이번 리팩토링에서 새로 만들어졌고, 정산/입찰/환불/결제는 기존에 도메인 컨슈머가 직접 알림을 보내던 것을 알림 도메인으로 옮긴 것이다. 관리자 정산 완료(NotificationSendEvent → NotificationEventHandler)는 이미 같은 디커플링 패턴이 적용돼 있어 변경하지 않았다.

2단계: NotificationCommandService — DB 저장 + Kafka 발행

메서드 호출 주체 동작
send(userId, type, message, relatedData) Kafka 컨슈머 3종
(NotificationRefundEventConsumer, NotificationPaymentEventConsumer, NotificationAuctionEventConsumer)		 sendInternal() 호출 →
① Notification 엔티티 저장 (알림 이력)
② NotificationEvent로 변환 후 Kafka notification 토픽에 발행 (key = userId, 파티션 결정용)
sendInternal(...) (직접 호출) 인프로세스 핸들러 4종
(NotificationSettlementEventHandler, NotificationBidEventHandler, NotificationOrderEscalationEventHandler, NotificationEventHandler)
인프로세스 핸들러(@TransactionalEventListener(AFTER_COMMIT) + @Transactional(REQUIRES_NEW))는 재시도/DLT 메커니즘이 없다. notificationCommandService.send(...) 호출이 예외를 던지면 각 핸들러에서 log.error로 흡수하고 끝나며, 해당 알림은 영구적으로 누락된다. Kafka 기반 컨슈머(환불/결제/경매)는 ack 실패 시 재처리/DLT(notification-dlt 등)가 가능하지만 인프로세스 경로는 그렇지 않다.

3단계: notification 토픽 → Redis Pub/Sub → WebSocket (워커서버)

이 구간은 pocat 리포지토리에 구현체가 없으며, 별도 워커서버 리포지토리에서 처리된다 (커밋 e9de856: "로직은 워커서버에서 구현"). 아래 내용은 pocat에 남아있는 기존 설계 문서 docs/notification-websocket.html을 기준으로 정리했으며, 워커서버 코드로 직접 검증되지는 않았다.

컴포넌트 (추정) 역할
NotificationKafkaConsumer notification 토픽 구독 (groupId: notification-ws-group) → Redis Pub/Sub 채널 notification:{userId}로 발행
Redis notification:{userId} 멀티 인스턴스 환경에서 어느 서버에 WebSocket 세션이 있어도 알림을 받을 수 있도록 브로드캐스트
NotificationRedisSubscriber 패턴 notification:* 구독 → SimpMessagingTemplate으로 /sub/notifications/{userId}에 WebSocket(STOMP) 전송
클라이언트 /sub/notifications/{userId} 구독 (JWT로 본인 userId만 구독 가능)
pocat 안에는 WebSocketAuthChannelInterceptor(global/security)만 존재하고, 이를 등록하는 @EnableWebSocketMessageBroker 설정이나 NotificationKafkaConsumer/NotificationRedisSubscriber 클래스는 찾을 수 없었다. 즉 WebSocket STOMP 엔드포인트와 Redis 구독/발행은 워커서버 쪽 구현으로 보인다.
