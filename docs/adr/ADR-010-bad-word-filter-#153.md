# ADR-010: 금지어 필터 — 클래스패스 파일 기반 메모리 적재·HTTP 400 거절 (#153)

## 맥락 (Context)

### 금지어 포함 콘텐츠 허용 — UGC 품질·신뢰도 저하

댓글(Comment), 자유게시글(FreePost), 거래게시글(TradePost), 채팅(Chat) 등 사용자 생성 콘텐츠(UGC) 전반에 걸쳐 금지어를 포함한 텍스트가 아무런 제약 없이 저장·노출되고 있었다. 플랫폼 신뢰도와 사용자 경험을 보호하기 위해 금지어 필터링 메커니즘이 필요하다.

### 필터링 방식 선택

금지어를 감지했을 때의 처리 방식으로 마스킹(예: `욕***`)과 요청 거절(HTTP 400) 두 가지 접근이 존재한다. 마스킹은 클라이언트에 데이터를 저장하면서 표시만 변경하므로 DB에 원본 금지어가 잔류하고, 후속 처리(검색, 인덱싱, 내보내기)에서 금지어가 다시 노출될 위험이 있다.

### 금지어 목록 관리 위치

금지어 목록을 DB에 저장하는 방식과 클래스패스 파일(`badwords.txt`)로 관리하는 방식이 존재한다. DB 방식은 실시간 갱신이 가능하지만 매 요청마다 DB I/O가 발생하거나 캐시 동기화 복잡도가 증가한다. 현재 요구사항 수준에서는 실시간 갱신이 필수 조건이 아니다.

---

## 결정 (Decision)

### 1. 금지어 감지 시 HTTP 400 거절 (마스킹 방식 채택 안 함)

금지어가 포함된 요청은 저장하지 않고 즉시 HTTP 400으로 거절한다.

- 마스킹 방식과 달리 금지어 원본이 DB에 잔류하지 않아 데이터 오염이 원천 차단된다.
- 클라이언트에 명확한 에러 응답(`CONTAINS_BAD_WORD`)을 반환하여 사용자가 재작성할 수 있도록 유도한다.
- 에러 코드: `CONTAINS_BAD_WORD (HTTP 400)`

### 2. `badwords.txt` 클래스패스 파일 기반 관리

금지어 목록을 DB가 아닌 클래스패스 리소스 파일 `badwords.txt`로 관리한다.

- 목록 변경은 파일 수정 후 재배포로 처리한다. 현재 요구사항에서 실시간 갱신은 필요하지 않다.
- DB 스키마 변경 없이 도입 가능하여 마이그레이션 비용이 없다.
- 파일 형식: 한 줄에 금지어 하나 (UTF-8 인코딩).

### 3. `BadWordFilterService` 싱글턴 컴포넌트 — 애플리케이션 기동 시 메모리 적재

`BadWordFilterService`를 Spring 싱글턴 컴포넌트(`@Component`)로 등록하고, 기동 시점에 `badwords.txt`를 읽어 금지어 목록을 메모리(`Set<String>`)에 적재한다.

- 요청마다 파일 I/O 또는 DB 조회 없이 메모리에서 직접 검사하여 성능 오버헤드를 최소화한다.
- 싱글턴이므로 목록이 애플리케이션 전체에서 단일 인스턴스로 공유된다.

### 4. 적용 범위

아래 4개 커맨드 서비스에서 저장 전 `BadWordFilterService`를 호출하여 금지어 포함 여부를 검사한다.

| 서비스 | 검사 대상 필드 |
|--------|--------------|
| `CommentCommandService` | 댓글 본문 |
| `FreePostCommandService` | 자유게시글 제목·본문 |
| `TradePostCommandService` | 거래게시글 제목·본문 |
| `ChatCommandService` | 채팅 메시지 본문 |

## 고려한 대안 (Alternatives Considered)

### 마스킹 방식 (감지 후 `***` 치환)

- **거절 이유**: 금지어 원본이 DB에 잔류하여 데이터 오염이 발생한다. 검색·인덱싱·데이터 내보내기 등 후속 처리에서 금지어가 재노출될 위험이 있다. 클라이언트에서도 마스킹 결과를 정상 저장된 것으로 오인할 수 있다.

### DB 저장 방식 (금지어 목록을 별도 테이블로 관리)

- **거절 이유**: 실시간 갱신이 현재 요구사항에 포함되지 않는다. DB 테이블 신규 생성, 마이그레이션 스크립트, 관리자 CRUD API 구현이 추가로 필요하여 이번 이슈 범위를 초과한다. 클래스패스 파일로 동등한 기능을 구현할 수 있다.

### 관리자 CRUD API 제공 (금지어 목록 런타임 관리)

- **거절 이유**: 현재 요구사항에 실시간 관리 기능이 없다. DB 저장 방식과 함께 범위 초과이며, 재배포 기반 관리로 충분하다. 필요 시 별도 이슈로 분리하여 구현한다.

### 실시간 리로드 (파일 변경 감지 후 메모리 재적재)

- **거절 이유**: 파일 시스템 와처(Watcher) 구현이 추가로 필요하고, 클러스터 환경에서 인스턴스 간 동기화 문제가 발생할 수 있다. 재배포 기반 적재로 충분하다.

### 대소문자·유니코드 정규화 (정규화 후 비교)

- **거절 이유**: 정규화 로직은 구현 복잡도를 높이고 한국어 특성상 오탐(false positive) 위험이 있다. 1차 구현에서는 단순 포함(contains) 검사로 시작하고 필요 시 별도 이슈로 확장한다.

### Aho-Corasick 알고리즘 적용

- **거절 이유**: 현재 금지어 목록 규모에서는 선형 `contains` 검사로 충분하다. Aho-Corasick은 수천 개 이상의 패턴 동시 검색 시 유의미한 성능 차이가 나타나며, 이를 위한 별도 라이브러리 의존성 추가가 이번 범위에 포함되지 않는다.

## 결과 (Consequences)

### 긍정적 영향

- 금지어가 포함된 콘텐츠가 DB에 저장되지 않아 플랫폼 데이터 품질이 보호된다.
- 서비스 계층에서 단일 컴포넌트(`BadWordFilterService`)를 재사용하므로 검사 로직이 중복되지 않는다.
- 메모리 기반 검사로 요청 처리 지연이 무시할 수준이다.
- DB 스키마 변경이 없어 마이그레이션 비용이 없다.

### 부정적 영향 / 트레이드오프

- 금지어 목록 변경 시 재배포가 필요하다. 긴급 차단이 필요한 금지어는 즉시 반영할 수 없다.
- 클러스터 환경에서 모든 인스턴스가 동일한 `badwords.txt`를 사용해야 하므로 빌드 산출물 관리가 중요하다.
- 대소문자 변형, 유니코드 우회, 자모 분리 등 우회 시도에 취약하다. 정규화·고급 알고리즘은 별도 이슈로 대응한다.
- 완전한 우회 차단은 txt 기반 단순 필터로는 불가 — 운영 정책상 best-effort 수준으로 허용한다.

### 새로운 파일

- `badwords.txt` — 클래스패스 금지어 목록 파일 (`src/main/resources/badwords.txt`)
- `BadWordFilterService` — 금지어 필터 싱글턴 서비스 컴포넌트

## 보안 고려사항

### 유니코드 우회 대응

- 검사 전 입력 텍스트에 `Normalizer.normalize(text, NFC)` + `toLowerCase(Locale.ROOT)` 를 적용한다.
- NFC 정규화는 NFD 방식으로 분리된 한글 자모(예: `ㅅ` + `ㅣ` + `ㅂ` + `ㅏ` + `ㄹ` 조합 형태)를 완성형으로 재결합하여, 자모 분리 우회 시도를 방어한다.
- `Locale.ROOT` 기반 소문자 변환은 터키어 등 로케일 의존 대소문자 변환 이슈를 차단한다.

### 남은 우회 가능성

- ZWJ(Zero Width Joiner) / ZWNJ(Zero Width Non-Joiner) 등 제로폭 문자를 금지어 사이에 삽입하는 우회 기법은 NFC 정규화 후에도 잔류할 수 있다.
- 해당 기법은 운영 정책상 **best-effort** 수준으로 허용한다. 완전 차단이 목표가 아니며, 발견 시 별도 이슈로 대응한다.

### 향후 개선 방향

- 금지어 목록 규모가 수천 개 이상으로 증가하거나 성능 요구가 높아질 경우 Aho-Corasick 알고리즘 기반 필터로 교체를 고려한다.
- 문맥·의도 기반 탐지가 필요한 경우 ML 기반 필터 도입을 고려한다.
- 두 경우 모두 `BadWordFilterService` 인터페이스를 유지한 채 내부 구현만 교체하는 방식으로 진행한다.
