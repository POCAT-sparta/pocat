# PRD #235 — 경매 활성화/종료 및 CardSync, Internal API 위임을 통한 배치 로직 통합

## 0. 메타 정보

- 관련 이슈: #235
- 관련 repo: `POCAT`(메인 백엔드), `pocat-batch`(스케줄 배치)
- 참조 패턴: ADR-018 / #222 (AI 리인덱스 — cursor 기반 청크 + internal API 위임, `MainAiReindexClient` / `InternalAiController` / `AiReindexTasklet`)
- 기존 internal API 인증: `InternalTokenAuthFilter` (`X-Internal-Token` 헤더, `/internal/**` 경로, 상수시간 비교)
- 기존 락 정책: `AuctionLifecycleService`가 `auction:lock:{auctionId}` Redisson 락을 트랜잭션 단위로 보유 (대기시간 0초, 트랜잭션 종료 후 자동 해제)

---

## 1. 기능 목적 (1줄)

pocat-batch가 재구현·축약했던 경매 활성화/종료 및 카드 동기화 로직을 메인 앱의 검증된 도메인 서비스(`AuctionLifecycleService`, `CardSyncService`)에 internal API로 위임하여, 누락된 ES 인덱싱·입찰 상태 갱신·이상거래 탐지·연관 엔티티 매핑·S3 업로드를 복원하고 두 repo 간 로직 중복을 제거한다.

## 2. 변경 1 — 경매 활성화/종료 Internal API 위임

### 2.1 Happy Path

#### (A) 경매 활성화 (Activation)

1. pocat-batch `AuctionActivationTasklet`(스케줄러 트리거)이 활성화 대상 경매 ID 목록을 조회한다.
   - 대상 조건: `status = APPROVED` (+ 승인 시각 도달 조건이 있다면 포함 — ARCHITECT가 메인 앱 `Auction.approve()` / `inspectedAt` 필드 기준으로 "활성화 가능 시점" 정의 확정)
2. 조회된 각 `auctionId`에 대해 `POST {main-app-base-url}/internal/auctions/{id}/activate` 호출.
   - 헤더: `X-Internal-Token`, `Idempotency-Key`(예: `auction-activate-{auctionId}-{jobExecutionId}`)
3. 메인 앱 `InternalAuctionController`(신규 엔드포인트)가 요청을 받아 `AuctionLifecycleService.activateApprovedAuction(auctionId)`를 그대로 호출.
   - 내부적으로: `auction:lock:{auctionId}` Redisson 락 획득(대기 0초) → 최신 상태 재조회(`status == APPROVED` 재검증) → `activate(startedAt, endedAt)`(경매 기간 **3일**, 기존 pocat-batch의 7시간 하드코딩 제거) → 커밋 후 ES 인덱싱(`AuctionEsIndexService.index`) → `AuctionActivatedEvent` 발행(Outbox) → 트랜잭션 종료 시 락 자동 해제
   - 반환값: `boolean` (처리됨=true / 이미 처리됨·상태 불일치로 스킵=false)
4. 메인 앱은 `ApiResponseDto<Boolean>`로 응답 (`true`=활성화 처리됨, `false`=스킵).
5. pocat-batch는 응답을 집계(성공/스킵/실패 카운트)하고 로그 기록 후 `RepeatStatus.FINISHED` 반환.

#### (B) 경매 종료 (Expiration)

1. pocat-batch `AuctionExpirationTasklet`(스케줄러 트리거)이 종료 대상 경매 ID 목록을 조회한다.
   - 대상 조건: `status = ACTIVE AND endedAt <= now` (메인 앱 `findAllByStatusAndEndedAtLessThanEqualOrderByEndedAtAsc`와 동일 패턴 — pocat-batch에 동등한 조회 쿼리가 이미 존재함, `AuctionRepository.findAllByStatusAndEndedAtLessThanEqualOrderByEndedAtAsc`)
2. 조회된 각 `auctionId`에 대해 `POST {main-app-base-url}/internal/auctions/{id}/close-expired` 호출.
   - 헤더: `X-Internal-Token`, `Idempotency-Key`(예: `auction-close-{auctionId}-{jobExecutionId}`)
3. 메인 앱 `InternalAuctionController`(신규 엔드포인트)가 `AuctionLifecycleService.closeExpiredAuction(auctionId)`를 그대로 호출.
   - 내부적으로: 락 획득 → 최신 상태 재검증(`isClosable`: `status == ACTIVE && endedAt <= now`) → 최고 입찰자 존재 여부 분기:
     - 입찰자 없음 → `markNoBidder()` → `AuctionEndedEvent`(loserIds=[]) 발행 → 커밋 후 ES `updateStatus(NO_BIDDER)` + `metrics.incrementEndedNoBidder()`
     - 입찰자 있음 → `markBidResults`(WON/LOST 갱신) → `end()` → 이상거래 탐지(`logAnomalyIfNeeded`) → `AuctionEndedEvent`(loserIds 포함) 발행 → 커밋 후 ES `updateStatus(ENDED)` + `metrics.incrementEndedSuccess()`
   - 반환값: `boolean` (처리됨=true / 상태 불일치로 스킵=false)
4. 메인 앱은 `ApiResponseDto<Boolean>`로 응답.
5. pocat-batch는 응답을 집계 후 `RepeatStatus.FINISHED` 반환.

### 2.2 신규 Internal API 스펙

| 항목 | 내용 |
|---|---|
| Endpoint | `POST /internal/auctions/{id}/activate` |
| 호출 서비스 | `AuctionLifecycleService.activateApprovedAuction(Long auctionId)` |
| 응답 | `200 OK`, `ApiResponseDto<Boolean>` (`true`=활성화됨, `false`=스킵) |
| 인증 | `X-Internal-Token` (`InternalTokenAuthFilter`, `/internal/**` 공통 적용) |

| 항목 | 내용 |
|---|---|
| Endpoint | `POST /internal/auctions/{id}/close-expired` |
| 호출 서비스 | `AuctionLifecycleService.closeExpiredAuction(Long auctionId)` |
| 응답 | `200 OK`, `ApiResponseDto<Boolean>` (`true`=종료됨, `false`=스킵) |
| 인증 | `X-Internal-Token` (`InternalTokenAuthFilter`, `/internal/**` 공통 적용) |

> 기존 `/internal/auctions/{id}/recover-buyout`과 동일 컨트롤러(`InternalAuctionController`)에 메서드 추가.

### 2.3 에러 케이스

| 케이스 | 메인 앱 동작 | pocat-batch 동작 |
|---|---|---|
| `auctionId` 존재하지 않음 | `AuctionException(AUCTION_NOT_FOUND)` → 4xx/5xx (ARCHITECT가 매핑 결정) | 실패로 집계, 로그 기록. 다음 회차 재시도 시 동일 결과 반복 가능 → 별도 "더 이상 대상 아님" 처리 필요 여부 검토 |
| 상태 불일치 (예: 이미 `ACTIVE`/`ENDED`, 또는 `APPROVED`가 아닌 상태에서 activate 호출) | `activateApprovedAuction`/`closeExpiredAuction`이 `false` 반환 → `ApiResponseDto.success(OK, false)` | 스킵으로 집계 (정상 흐름, 재시도 불필요) |
| Internal Token 인증 실패 (`X-Internal-Token` 누락/불일치) | `InternalTokenAuthFilter`에서 401 반환, 컨트롤러 도달 전 차단 | 인증 실패로 집계, 즉시 실패 처리 (`HttpClientErrorException` 4xx) — 재시도해도 동일하게 실패하므로 알람/모니터링 대상 |
| 락 획득 실패 (`auction:lock:{id}` 이미 점유 중 — 동시에 다른 프로세스가 처리 중) | `AuctionException(AUCTION_LOCK_FAILED)` (대기 0초이므로 즉시 실패) → 5xx 매핑 가능성 | 실패로 집계, 다음 배치 회차에서 재시도(멱등) |
| 중복 요청 (같은 `auctionId`에 대해 같은 회차 내 또는 다른 회차에서 재호출) | `activateApprovedAuction`/`closeExpiredAuction`이 최신 상태 재조회 후 조건 불충족이면 `false` 반환 → 멱등 보장 | 스킵으로 집계 |
| internal API 타임아웃 | (해당 없음 — 호출 측 이슈) | `RestTemplate` 타임아웃 발생 → 재시도(지수 백오프, 최대 N회 — `MainAppBuyoutClient`/`MainAiReindexClient` 패턴 참고) 후 실패 집계, 다음 회차 재시도 |
| internal API 4xx (인증 실패 제외, 예: `@Positive` 검증 실패 — `auctionId <= 0`) | `400 Bad Request` | 즉시 실패로 집계 (재시도 없이 스킵, `HttpClientErrorException` 처리) |
| internal API 5xx (메인 앱 내부 오류 — DB 장애, ES 인덱싱 예외 등) | `500 Internal Server Error` | 재시도(지수 백오프) 후 실패 집계, 다음 배치 회차에서 재시도(멱등) |

### 2.4 취소·롤백 조건

- **internal API 실패 시 pocat-batch 측 처리**: pocat-batch는 자체 DB 상태를 변경하지 않으므로(이미 위임 완료 후 두 repo 도메인 로직 직접 호출 제거됨) 롤백 대상 없음. 실패한 `auctionId`는 다음 배치 회차의 대상 조회 쿼리(`status = APPROVED` 또는 `status = ACTIVE AND endedAt <= now`)에서 자동으로 재포함되어 재시도됨.
- **멱등성 보장 방식**:
  - 메인 앱: `activateApprovedAuction`/`closeExpiredAuction` 자체가 "최신 상태 재조회 → 조건 검증 → 불충족 시 false 반환" 구조이므로, 동일 요청이 여러 번 들어와도 실제 도메인 변경은 최초 1회만 발생.
  - pocat-batch: `Idempotency-Key` 헤더 전달(ADR-018 패턴 준수) — 단, 현재 `activateApprovedAuction`/`closeExpiredAuction`은 `Idempotency-Key`를 사용하지 않으므로(상태 기반 멱등), 메인 앱 컨트롤러가 이 헤더를 실제로 활용할지 여부는 ARCHITECT 결정 사항. (참고: `MainAppBuyoutClient.recoverBuyout`도 헤더는 전달하나 컨트롤러는 미사용 — 동일 선례 존재)
- **트랜잭션 경계**: 락 획득~해제, 상태 변경~ES 인덱싱~이벤트 발행까지 전부 메인 앱 `AuctionLifecycleService` 내부에서 일관되게 처리됨 (변경 없음, 기존 동작 그대로 internal API 경로로 노출).

## 3. 변경 2 — CardSync Internal API 위임

### 3.1 Happy Path

1. pocat-batch `CardSyncTasklet`(스케줄러 트리거)이 TCGdex API(`/v2/en/sets`, `/v2/en/sets/{setId}`, `/v2/en/cards/{tcgdexId}`)를 호출하여 동기화 대상 카드 원시 데이터를 수집한다.
   - **TCGdex 호출 위치는 현 구조(pocat-batch 측 유지) 가정** — 변경 시 ARCHITECT 결정 필요 (3.5 범위 외 참조)
2. pocat-batch는 신규 카드(이미 존재하는 `tcgdexId`는 `findByTcgdexIdIncludingDeleted`로 스킵)에 대해 청크 단위로 데이터를 구성한다.
   - 청크 구성 방식(요청 body 형태)은 RESEARCH 결과에 따라 결정:
     - 옵션 A: pocat-batch가 TCGdex 원시 데이터(또는 정규화된 카드 DTO 목록)를 청크로 묶어 메인 앱에 전달 → 메인 앱이 `findOrCreate` + S3 업로드 + ES 인덱싱 수행
     - 옵션 B: pocat-batch가 신규 `tcgdexId` 목록만 전달 → 메인 앱이 TCGdex 재조회 + 전체 동기화 로직 수행 (TCGdex 호출 중복 발생 — 비효율 가능성, ARCHITECT 검토)
3. `POST {main-app-base-url}/internal/cards/sync` 호출 (ADR-018 패턴: `X-Internal-Token`, `Idempotency-Key`).
4. 메인 앱 `InternalCardSyncController`(신규)가 `CardSyncService`의 기존 로직(연관 엔티티 `findOrCreate`: `Series`/`PokemonSet`/`Pokemon`, S3 이미지 업로드(`resolveImageUrl`), `Card` 저장, `cardCommandService.indexCard`)을 청크 단위로 호출.
5. 메인 앱은 처리 통계(`ReindexChunkResponse`와 유사한 `CardSyncChunkResponse` — 예: `processedCount`, `syncedCount`, `skippedCount`)를 `ApiResponseDto<CardSyncChunkResponse>`로 응답.
6. pocat-batch `CardSyncTasklet`은 `AiReindexTasklet`과 동일한 구조(`MainAiReindexClient` 패턴 참고)로 thin orchestrator화:
   - cursor/오프셋 기반으로 다음 청크 처리 또는 종료
   - 청크 호출 실패 시 로그 후 다음 청크로 진행 (전체 작업 중단 없음, `AiReindexTasklet`의 `catch (Exception e) { log.warn(...) }` 패턴과 동일)

### 3.2 신규 Internal API 스펙 (초안 — 세부는 ARCHITECT 결정)

| 항목 | 내용 |
|---|---|
| Endpoint | `POST /internal/cards/sync` |
| 호출 서비스 | `CardSyncService`의 `syncSet`/`findOrCreate`/S3 업로드/`indexCard` 로직 (청크 단위 재구성 필요) |
| 요청 body | 카드 청크 데이터 또는 `tcgdexId`/`cardId` 목록 — RESEARCH 결과에 따라 결정 |
| 응답 | `202 Accepted`, `ApiResponseDto<Void>` |
| 인증 | `X-Internal-Token` (`InternalTokenAuthFilter`) |
| 멱등성 | `Idempotency-Key` 헤더 (ADR-018 패턴) — `tcgdexId` 기준 `existsByTcgdexId`/`findByTcgdexIdIncludingDeleted` 체크로 자연 멱등 보장 가능 |

### 3.3 에러 케이스

| 케이스 | 메인 앱 동작 | pocat-batch 동작 |
|---|---|---|
| 요청 body 비어있음/null | `400 Bad Request` (`InternalAiController.handleInvalidRequestBody` 패턴 참고) | 즉시 실패 집계, 해당 청크 스킵 |
| 청크 내 일부 `tcgdexId` 이미 존재 | 해당 항목은 스킵 처리, 나머지는 정상 동기화 (`syncedCount`/`skippedCount` 분리 집계) | 응답 집계만 수행 |
| TCGdex 카드 상세 조회 실패 (메인 앱이 TCGdex 호출하는 옵션 B인 경우) | 해당 카드 스킵, 로그(`[CARD_SYNC] 카드 처리 실패`), 나머지 계속 처리 | 응답 집계 |
| S3 업로드 실패 | 기존 `resolveImageUrl` catch 블록과 동일 — TCGdex 원본 URL로 폴백, 동기화는 계속 진행 (실패로 취급 안 함) | 영향 없음 |
| DB 저장 시 `DataIntegrityViolationException` (동시성 중복) | 기존 `syncSet`과 동일 — 로그 후 스킵, 카운트 미증가 | 영향 없음 |
| Internal Token 인증 실패 | 401, 컨트롤러 도달 전 차단 | 인증 실패 집계, 즉시 실패 (재시도해도 동일 — 모니터링 대상) |
| internal API 타임아웃/5xx | 처리 중단(부분 커밋 가능성 — 트랜잭션 경계는 ARCHITECT 결정) | `AiReindexTasklet` 패턴과 동일하게 해당 청크 실패 로그 후 다음 청크로 진행 (전체 Job은 `FINISHED`) |
| internal API 4xx (검증 실패) | `400 Bad Request` | 즉시 스킵, 해당 청크 재시도 없음 |

### 3.4 취소·롤백 조건

- **멱등성 보장**: `tcgdexId` 기준 존재 여부 체크(`existsByTcgdexId` / `findByTcgdexIdIncludingDeleted`)가 메인 앱 측 `CardSyncService` 로직에 이미 내재되어 있음 — 동일 청크가 재전송되어도 신규 카드만 생성됨.
- **internal API 실패 시 pocat-batch 측 처리**: `AiReindexTasklet`과 동일하게 실패한 청크는 로그 기록 후 건너뛰고 다음 청크 진행. 다음 스케줄 회차에서 동일 `tcgdexId`가 다시 "미존재"로 판정되면 재시도됨(자연 멱등).
- **부분 실패 처리**: 한 청크 내 일부 카드만 실패해도 나머지는 정상 처리 (응답에 `processedCount`/`syncedCount`/`failedCount` 등으로 구분 — 세부 필드명은 ARCHITECT 결정).

## 4. 비기능 요구사항

### 4.1 동시성

- **락 소유권 이전 후 동작 보장**: `auction:lock:{auctionId}` Redisson 락의 획득/해제는 메인 앱 `AuctionLifecycleService`로 일원화. pocat-batch `AuctionActivationTasklet`/`AuctionExpirationTasklet`의 자체 `redissonClient.getLock(...)` / `tryLock(0, 30, TimeUnit.SECONDS)` 호출 코드는 **완전 제거**.
  - 검증 필요: pocat-batch와 메인 앱이 **동일 Redis 인스턴스/클러스터**를 `RedissonClient`로 바라보는지 확인 (락 키 네임스페이스 `auction:lock:{id}`가 메인 앱 Redis에만 존재하면, pocat-batch 측 중복 락 코드 제거는 안전하지만, 두 서비스가 다른 Redis를 쓴다면 락 자체가 무의미해지므로 ARCHITECT가 인프라 구성 확인 필요)
  - 동시에 같은 `auctionId`에 대해 activation/expiration 배치와 사용자 트래픽(예: 즉시구매, Redis 만료 이벤트 리스너)이 경쟁할 수 있으나, 이는 기존 `AuctionLifecycleService` 락 정책으로 이미 처리되는 영역 — internal API 경로 추가로 인한 신규 동시성 이슈 없음.
- **CardSync 동시성**: 기존 `syncAll`에 명시적 락 없음 (TODO: Spring Batch 적용 주석 존재). internal API 위임 후에도 동시 실행 시 `DataIntegrityViolationException` catch로 방어되는 기존 수준 유지. 별도 락 신설은 범위 외.

### 4.2 성능 목표

- **HTTP 호출 횟수**:
  - 경매 활성화/종료: 대상 `auctionId` 1건당 internal API 1회 호출 (N+1 패턴 — 대상 건수가 일반적으로 적음(수십 건 이하)을 전제. 대량화 시 청크 API로 전환 필요 여부는 ARCHITECT 검토 — #222에서 채택한 "청크 단위" 패턴과의 일관성 고려)
  - CardSync: 청크 단위 호출 (`AiReindexTasklet`의 `CHUNK_SIZE = 100` 참고 — 동일/유사 크기 적용 검토)
- **타임아웃**:
  - activate/close-expired: 단일 경매 처리이므로 `AuctionLifecycleService` 트랜잭션(락 대기 0초 + DB + ES 인덱싱) 기준 합리적 짧은 타임아웃 설정 (예: connect 5s / read 10s — `CardSyncService.createRestTemplate()` 기존 설정값 참고)
  - cards/sync: 청크 크기에 비례하여 read timeout 상향 필요 (S3 업로드 포함 시 청크당 처리 시간 증가 고려)
  - 재시도: `MainAiReindexClient`/`MainAppBuyoutClient` 패턴과 동일하게 최대 3회, 지수 백오프(1s → 2s → 4s), 4xx는 즉시 스킵(재시도 없음)

### 4.3 모니터링/메트릭

- 기존 `AuctionMetrics.incrementEndedNoBidder()` / `incrementEndedSuccess()`는 메인 앱 `AuctionLifecycleService` 내부에서 그대로 발생 — internal API 경로로도 정상 수집됨 (별도 작업 불필요).
- pocat-batch 측 신규 메트릭(activate/close-expired/cards-sync 성공·스킵·실패 카운트)은 기존 Tasklet 로그 패턴(`log.info("... 완료: {} 개 ...")`) 수준으로 충분한지, 별도 Micrometer 메트릭 신설이 필요한지 ARCHITECT 검토.

## 5. 명시적 범위 외 (ARCHITECT 결정 위임)

다음 항목은 본 PRD에서 결정하지 않으며, ARCHITECT(BLUEPRINT) 단계에서 확정한다:

1. **pocat-batch `AuctionBatchService` 완전 삭제 여부** — `activateAuction`/`endAuction` 메서드가 internal API 위임 후 호출되지 않게 되면, 클래스 자체를 삭제할지 또는 미사용 상태로 유지(향후 재사용 가능성)할지.
2. **pocat-batch `Auction` 엔티티의 `activate()`/`end()` 메서드, `AuctionStatus` enum 사용 여부** — internal API 위임 후 pocat-batch에서 `Auction` 엔티티의 상태 변경 메서드가 더 이상 호출되지 않을 경우, 엔티티/enum 자체는 대상 조회 쿼리(`findAllByStatus`, `findAllByStatusAndEndedAtLessThanEqualOrderByEndedAtAsc`)에서 계속 필요하므로 완전 삭제는 불가 — 단, `activate()`/`end()` 메서드 자체의 제거 여부.
3. **pocat-batch `AuctionBidRepository`, `OutboxEventWriter` 사용 여부** — `AuctionBatchService` 삭제 시 이들의 잔존 사용처 확인 및 정리 필요 여부.
4. **CardSync internal API 요청 body 형식 최종 결정** (3.2의 옵션 A/B) — TCGdex 호출을 pocat-batch와 메인 앱 중 어느 쪽에서 수행할지에 따라 API 설계가 크게 달라짐. RESEARCH 단계 결과를 반영하여 ARCHITECT가 확정.
5. **활성화 대상 조회 조건의 "승인 시각 도달" 여부** — 현재 메인 앱 `AuctionRepository.findAllByStatus(APPROVED)`에는 시각 기반 필터가 없음. `status = APPROVED`만으로 즉시 활성화 대상으로 간주할지, 별도 "활성화 예정 시각" 필드/조건이 필요한지 확인.
6. **internal API 에러 상태 코드 매핑** — `AUCTION_NOT_FOUND`, `AUCTION_LOCK_FAILED` 등 도메인 예외를 `InternalAuctionController`에서 어떤 HTTP 상태로 매핑할지 (4xx vs 5xx, 기존 `recoverBuyout`은 `IllegalStateException`→200, 기타 예외→500 패턴).
7. **`Idempotency-Key` 헤더의 실제 서버측 활용 여부** — activate/close-expired는 상태 기반 자연 멱등이라 헤더 미사용도 가능 (기존 `recoverBuyout` 선례). 패턴 일관성을 위해 수신/로깅만 할지, 실제 dedup 키로 사용할지.
8. **대량 활성화/종료 시 청크화 필요성** — 현재는 ID별 1회 호출 가정. 동시 대상 건수가 많아질 경우 #222식 청크 API로 전환할지 여부.
9. **CardSync의 TCGdex 호출 위치 변경 여부** — 현 구조(pocat-batch 유지) vs 메인 앱 이전, 호출 중복 최소화 방안.
