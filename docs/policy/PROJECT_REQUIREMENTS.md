> 지금 시장에서 가치 있는 개발자는 **"AI로 개발하면서, AI 기능을 만드는"** 사람입니다.

### 프로젝트 개요

본 최종 프로젝트는 **거래(Transaction)가 존재하는 서비스**를 자유롭게 기획하고, 거래 시스템의 핵심 패턴과 AI 기능 통합을 함께 구현하는 것을 목표로 합니다.

<aside>
💡

**커머스를 이렇게 정의합니다.**

커머스 = 쇼핑몰 ❌

커머스 = **거래 시스템의 핵심 문제를 다룰 줄 아는 것** ✅

핵심은 **"무엇을 파느냐"가 아니라 "거래 시스템의 핵심 문제를 어떻게 해결하느냐"** 입니다.

</aside>

### 자유 주제 원칙

거래(Transaction)가 존재하는 서비스라면 주제는 **완전히 자유**입니다.

- 💡 도메인 예시 모아보기


    | 도메인 예시 | 거래의 핵심 문제 |
    | --- | --- |
    | 이커머스 쇼핑몰 | 재고 동시성, 주문 상태 전이, 결제 정합성 |
    | 중고거래 플랫폼 | 예약-구매 충돌, 신뢰 시스템, 상태 관리 |
    | 티켓 예매 | 좌석 선점, 결제 타임아웃, 대기열 처리 |
    | 음식 배달 | 실시간 상태 추적, 배달 시간 예측, 주문 취소 정책 |
    | 숙박 예약 | 날짜 충돌 방지, 부분 환불, 예약 변경 정책 |
    | 구독 서비스 / SaaS | 반복 결제, 플랜 변경, 구독 취소 시 데이터 처리 |
    | 강의 플랫폼 | 수강 권한 관리, 환불 정책, 진도율 추적 |
    | 공연·스포츠 예매 | 동시 접속 폭주, 등급별 좌석 관리, 양도 정책 |
    | 병원·클리닉 예약 | 시간대 중복 방지, 노쇼 처리, 대기 순번 관리 |
    | 렌탈·공유 서비스 | 자원 점유 충돌, 반납 지연 패널티, 손상 보증금 처리 |
    | 경매 플랫폼 | 입찰 동시성, 낙찰 처리, 시간 마감 정합성 |

### 이번 프로젝트에서 경험하는 것

"어떤 문제를 해결하고 싶은가?"

"어떤 사용자에게 어떤 경험을 주고 싶은가?"

이 두 질문에서 스스로 고민하며 **`기획 → 도메인 설계 → 구조 설계 → 구현 → 배포`** 의 실제 서비스 개발 사이클을 경험합니다.

- **백엔드 설계 역량**: 도메인 모델링, 인증/인가, 동시성 제어, 성능 최적화·캐싱, 로그·모니터링
- **AI Engineering 역량**: 프롬프트 엔지니어링, Tool Calling, 장애 격리·환각 방어, RAG, 멀티턴 대화
- **AI Native 역량**: AI로 SA 작성·검토, 문서화, 트러블슈팅 기록 등 개발 워크플로우 전반에 AI 내재화
- **기술 선택 근거 문서화**: 매 주차 기술 선택 이유와 트레이드오프를 기록하는 습관
- **협업 경험**: 기획부터 회고까지 전체 사이클 완주

## 2️⃣ 프로젝트 요구사항

### **공통 요구사항**

<aside>
🤖

아래 공통 항목은 모든 팀이 프로젝트 전반에 걸쳐 실천해야 하는 AI 활용 방식입니다.

"AI를 도구로 사용했는가"가 아니라, **"AI 결과물을 비판적으로 검토하고 팀의 판단을 반영했는가"** 가 평가 기준입니다.

</aside>

### 1. 기획·설계 단계에서 AI 활용

AI를 활용하여 요구사항 정의, 유저 스토리, ERD, API 명세서 등 SA 초안을 생성하고, 팀이 비판적으로 검토·수정하여 완성한다.

- [ ]  AI를 활용해 도메인 분석, ERD, API 명세 초안을 생성한다.
- [ ]  AI 초안을 그대로 사용하지 않고 팀이 비즈니스 로직·예외 케이스·실현 가능성을 기준으로 검토·수정하여 완성한다.

### 2. AI를 활용한 포트폴리오·문서화

AI를 활용하여 프로젝트 문서를 작성하되, 팀의 실제 경험과 판단을 반영한 최종본으로 완성한다.

- [ ]  AI를 활용해 README, 기술 선택 근거, 트러블슈팅 기록 등 문서 초안을 생성한다.
- [ ]  생성된 초안에 실제 구현 내용·수치·판단 근거를 반영하여 팀의 경험이 드러나는 최종본으로 완성한다.

### **백엔드 필수 요구사항**

<aside>
💡

아래 11개 항목은 모든 팀이 구현해야 하는 **백엔드 필수 요구사항**입니다.

단순 구현에서 끝내지 않고, **기술 선택 근거와 개선 전후 수치를 문서화**하는 것이 핵심입니다.

</aside>

### 1. 테스트 코드

핵심 비즈니스 로직에 대한 단위 테스트와 통합 테스트를 각 1개 이상 작성한다.

- [ ]  핵심 비즈니스 로직 단위 테스트 1개 이상 (성공 + 실패/예외 케이스 포함)
- [ ]  통합 테스트 1개 이상 (실제 흐름 기반)
- [ ]  CI 파이프라인에서 테스트 자동 실행 구성

### 2. 도메인 설계 및 CRUD

JPA 기반으로 핵심 엔티티를 설계하고 기본 CRUD를 구현한다. 도메인 간 관계와 비즈니스 정책이 코드에 반영되어야 한다.

- [ ]  서비스 요구사항 기반 핵심 엔티티 정의 및 관계 설계 (1:N, N:M 등)
- [ ]  비즈니스 정책과 상태 전이가 엔티티/서비스 코드에 반영됨
- [ ]  JPA Repository 기반 CRUD 구현
- [ ]  도메인 규칙 위반 시 예외 처리

### 3. 계층형 아키텍처

관심사 분리 원칙에 따라 레이어를 나누고, 각 레이어의 역할과 책임을 명확히 한다. 아키텍처 방식은 자유롭게 선택하되, 선택 근거를 문서화한다.

- [ ]  아키텍처 방식 선택 및 근거 문서화
- [ ]  각 레이어의 책임 범위를 벗어난 코드 없는지 확인
- [ ]  레이어 간 의존 방향이 선택한 아키텍처에 맞게 올바르게 유지됨

### 4. 인증/인가

적절한 인증 방식을 선택하여 구현하고, 미인증 요청에 대한 응답 처리를 포함한다. 기술 선택 근거를 문서화한다.

- [ ]  인증 방식 선택 및 선택 근거 문서화
- [ ]  인증이 필요한 API에 대한 인가 처리 구현
- [ ]  미인증 요청에 대해 적절한 HTTP 상태 코드 응답
- [ ]  인증 실패 시나리오 테스트 포함

### 5. 배포 및 CI/CD

외부에서 접근 가능한 환경에 배포하고, 코드 변경이 자동으로 반영되는 파이프라인을 구성한다. 배포 방식 선택 근거를 문서화한다.

- [ ]  외부 접근 가능한 배포 환경 구성 (고정 DNS 주소)
- [ ]  GitHub Actions 기반 CI/CD 파이프라인 구성 (빌드 → 테스트 → 배포)
- [ ]  배포 방식 선택 근거 문서화
- [ ]  민감 정보 관리

### 6. 타입 안전 쿼리

복잡한 조건 조회가 필요한 지점을 식별하고, 타입 안전하게 쿼리를 작성할 수 있는 방법을 선택하여 적용한다. 기술 선택 근거를 문서화한다.

- [ ]  복잡한 조건 조회가 필요한 지점 식별
- [ ]  타입 안전 쿼리 방식 선택 및 근거 문서화
- [ ]  선택한 방식으로 복합 조건 조회 구현 (페이징·정렬 포함)

### 7. 동시성 제어

동시 요청이 발생할 수 있는 지점을 식별하고 적절한 처리 전략을 선택하여 적용한다. 전략 선택 근거와 동시 요청 테스트 결과를 문서화한다.

- [ ]  동시 요청 발생 가능 지점 식별
- [ ]  처리 전략 선택 및 근거 문서화
- [ ]  락 획득 실패 시 전략 정의
- [ ]  동시 요청 테스트 코드 작성 및 결과 문서화

### 8. 부하 테스트

목표 트래픽 기준을 직접 설정하고 부하 테스트를 수행한다. 병목 지점을 식별하고 개선 전후 수치를 비교하여 문서화한다.

- [ ]  목표 트래픽 기준 직접 설정 및 설정 근거 문서화
- [ ]  부하 테스트 도구 선정 및 다양한 시나리오 기반의 부하 테스트 수행
- [ ]  Latency(P95/P99), Throughput(RPS), Error Rate 등 기록
- [ ]  병목 지점 식별 및 개선 전후 수치 비교 문서화

### 9. 성능 병목 개선

느린 쿼리와 병목 지점을 식별하고 개선한다. 개선 전후 성능 변화를 수치로 문서화한다.

- [ ]  느린 쿼리 식별
- [ ]  EXPLAIN 기반 실행 계획 분석
- [ ]  개선 적용
- [ ]  개선 전후 조회 성능 수치 비교 문서화 (Before → After)

### 10. 캐싱 전략

조회 빈도가 높거나 데이터 규모가 큰 지점을 식별하여 캐싱을 적용한다. 어떤 지점에 왜 캐싱했는지, 만료 정책을 어떻게 설정했는지 근거를 문서화한다.

- [ ]  캐싱 대상 지점 식별 및 선택 근거 문서화
- [ ]  캐싱 기술 선택
- [ ]  TTL 및 만료 정책 설정 근거 문서화
- [ ]  캐시 적용 전후 조회 성능 수치 비교

### 11. 로그·모니터링

시스템 상태와 API 호출 흐름을 관찰할 수 있는 환경을 구성한다. 어떤 지표와 로그를 왜 수집했는지, 수집한 데이터에서 어떤 인사이트를 얻을 수 있는지 근거를 문서화한다.

- [ ]  로그 수집 환경 구성 (구조화 로그, 로그 레벨 정책)
- [ ]  모니터링 지표 선정 및 수집 근거 문서화
- [ ]  수집한 데이터에서 얻을 수 있는 인사이트 기술
- [ ]  장애/이상 상황 감지 가능 여부 확인

### **백엔드 도전 요구사항**

<aside>
💡

아래 4개 항목은 **백엔드 도전 요구사항**입니다.

필수 항목을 모두 완료한 팀이 추가로 도전합니다. 기술 선택 근거와 개선 효과를 수치로 비교하는 것이 핵심입니다.

</aside>

### 1. 실시간 메시징

실시간 양방향 통신이 필요한 기능을 정의하고 적절한 방식을 선택하여 구현한다. 기술 선택 근거를 문서화한다.

- [ ]  실시간 통신이 필요한 기능 정의 (채팅, 알림, 상태 업데이트 등)
- [ ]  기술 선택 및 근거 문서화
- [ ]  메시지 브로커 선택 및 근거 문서화
- [ ]  인증된 사용자만 접근 가능한 구조 보장
- [ ]  실시간 메시지 DB 영구 저장 처리

### 2. 비동기 이벤트 처리

동기 처리의 한계가 드러나는 지점을 식별하고, 비동기 메시지 기반으로 전환한다. 기술 선택 근거와 동기 처리 대비 개선 효과를 문서화한다.

- [ ]  동기 처리 시 병목이 발생하는 지점 식별 및 문서화
- [ ]  비동기 처리 기술 선택 및 근거 문서화
- [ ]  동기 처리 대비 개선 효과 수치 비교 문서화
- [ ]  메시지 처리 실패 시 대응 전략 적용

### 3. 배포 고도화

현재 배포 구조의 한계를 정의하고, 가용성·확장성·무중단 배포 중 개선할 지점을 선택하여 적용한다. 개선 전후를 비교하여 문서화한다.

- [ ]  현재 배포 구조의 한계 분석 및 문서화
- [ ]  개선 방향 선택 및 근거 문서화
- [ ]  개선 전후 가용성·배포 소요 시간·장애 복구 시간 비교 문서화

### 4. 트래픽 제어

특정 API에 대한 과도한 요청을 제어하는 메커니즘을 구현한다. 임계값 설정 근거와 초과 요청에 대한 응답 처리를 문서화한다.

- [ ]  과도한 요청이 발생할 수 있는 API 식별
- [ ]  요청 제어 메커니즘 구현
- [ ]  임계값 설정 근거 문서화
- [ ]  초과 요청 시 `429 Too Many Requests` 응답 처리
- [ ]  부하 테스트로 실제 동작 검증

### 1. LLM 구조화 출력 및 프롬프트 엔지니어링

LLM 응답을 정의된 스키마로 파싱하여 DB에 저장하고, 프롬프트를 체계적으로 관리하며 개선 이력을 문서화한다.

- [ ]  LLM 응답을 DTO/JSON Schema로 파싱하여 DB에 저장한다.
- [ ]  응답 길이 상한(`max_tokens`)과 창의성 수준(`temperature`)을 명시적으로 설정하고 선택 근거를 문서화한다.
- [ ]  도메인·카테고리별 프롬프트 템플릿을 최소 2개 이상 분기 처리한다.
- [ ]  프롬프트를 코드에 하드코딩하지 않고 서버 재배포 없이 수정 가능한 구조로 관리한다.
- [ ]  프롬프트 개선 이력을 최소 3회 기록한다. (변경 동기 → 토큰 변화 → 출력 품질 변화 → 다음 개선 방향)
- [ ]  모델 선택 근거를 문서화한다.
- 💡 도메인 적용 예시

    <aside>
    🛒

  **커머스: 상품 리뷰 자동 요약**

  리뷰 텍스트를 LLM에 넘기면 아래 JSON 스키마로 파싱하여 DB에 저장합니다.

    ```json
    {
      "summary": "가벼우면서 보온성이 좋다는 의견이 많습니다",
      "pros": ["가볍다", "보온성 우수"],
      "cons": ["주머니가 작다"],
      "keywords": ["경량", "보온", "핏"],
      "sentiment": "POSITIVE"
    }
    ```

  카테고리별 프롬프트 분기:

    - 의류 → 감성적·착용감 중심 톤, 핏·사이즈·소재감 강조
    - 전자제품 → 간결·전문적 톤, 성능·배터리·호환성 강조
    - 식품 → 식욕 자극·생생한 묘사 톤, 맛·식감·신선도 강조
    </aside>

  **다른 도메인 예시**

    - 숙박 예약: 숙소 설명 자동 생성. 펜션은 감성적 톤, 비즈니스호텔은 실용적 톤으로 분기
    - 중고거래: 사진·한 줄 설명 → 카테고리별 상세 설명 자동 생성 (가전: 스펙 중심 / 의류: 상태·착용감 중심)

### 2. Tool Calling 기반 AI-백엔드 API 연동

Spring AI `@Tool`로 백엔드 API를 LLM과 연동하여 자연어 요청에 실시간 데이터를 포함한 응답을 반환하고, 실패 시 자연어로 안내하는 흐름을 구현한다.

- [ ]  `@Tool`로 최소 2개 이상의 백엔드 API를 LLM과 연동한다.
- [ ]  사용자의 자연어 요청에 대해 실시간 데이터를 포함한 자연어 응답을 반환한다.
- [ ]  Tool 호출 실패 시 실패 컨텍스트를 LLM에 전달하여 사용자에게 자연어로 안내하는 흐름을 구현한다.
- 💡 도메인 적용 예시

    <aside>
    🛒

  **커머스: AI 쇼핑 어시스턴트**

    ```
    [정상 상황] 사용자: "3만원 이하 반팔티 중에 재고 있는 거 추천해줘"
      → LLM이 searchProducts(category="반팔티", maxPrice=30000) 호출
      → LLM이 자동으로 checkStock(productId=1), checkStock(productId=2) 호출
      → "가격 조건에 맞는 반팔티 3개를 찾았어요.
         이 중 재고가 있는 상품은 A티실릴(M·L)'입니다."
    
    [장애 상황] checkStock API 타임아웃 발생
      → LLM이 "재고 확인이 어렵습니다.
         조건에 맞는 반팔티 3개를 찾았는데, 재고는 잠시 후 다시 확인해드릴게요." 안내
    ```

  Tool 예시: `searchProducts` / `checkStock` / `getDeliveryETA`

  > 하나의 요청에서 LLM이 여러 Tool을 순차적으로 호출하여 결과를 합성하는 것이 핵심입니다.
  >
    </aside>

  **다른 도메인 예시**

    - 배달: "30분 안에 오는 치킨집" → 가게 검색 API + 배달 시간 예측 API 호출
    - 예약: "이번 주 토요일 2명 이탈리안" → 가게 검색 API + 예약 가능 여부 조회 API 호출

### 3. AI 기능 장애 격리 및 비용 인식 설계

LLM API 장애 시 Fallback으로 핵심 서비스 정상 동작을 보장하고, 토큰 사용량·응답 지연·에러율을 시각화한다.

- [ ]  LLM API 장애(타임아웃·Rate Limit·5xx 등) 시 Fallback을 최소 2가지 구현한다.
- [ ]  AI 기능 장애가 핵심 서비스(주문·결제 등)에 영향을 주지 않는지 확인한다.
- [ ]  환각 방어를 최소 1가지 이상 구현한다.
- [ ]  토큰 사용량·응답 시간·에러율 로깅을 적용하고 장애 시나리오 테스트 코드를 작성한다.
- [ ]  메트릭 수집 도구를 선택하여 토큰 사용량·응답 지연을 자동 수집한다. 기술 선택 근거를 문서화한다.
- [ ]  모델별 누적 토큰·P95 응답 지연·에러율을 한 화면에서 확인할 수 있는 대시보드를 구성한다.
- 💡 도메인 적용 예시

    <aside>
    🛒

  **커머스: "AI 리뷰 요약이 죽으면, 상품 구매도 안 되나?"**

  정답은 "아니요"여야 합니다. 장애 격리란 바로 이 분리를 보장하는 것입니다.

    ```
    [정상 상태]
    상품 상세 페이지 → 리뷰 요약(AI) ✅ + 구매 버튼 ✅
    
    [AI 장애 상태]
    상품 상세 페이지 → 리뷰 요약: "요약을 불러올 수 없습니다" + 구매 버튼 ✅
    ```

  Fallback 예시:

    - 타임아웃(5초 초과) → 캐시된 이전 요약 반환 또는 안내 메시지
    - Rate Limit(429) → Circuit Breaker 오픈, 기본 응답 반환
    - 환각 방어 → 존재하지 않는 상품 정보 생성 시 "정확한 답변을 드리기 어렵습니다" 반환

  비용 로깅 항목: `{requestId, promptTokens, completionTokens, latencyMs, model, status, errorType}`

    </aside>

### 1. RAG 파이프라인 구축

도메인 데이터를 임베딩·벡터DB에 저장하고, 시맨틱 검색 결과를 LLM 컨텍스트에 주입하여 출처 표시 답변을 생성하는 RAG 전체 사이클을 구현한다.

- [ ]  도메인 데이터를 임베딩하여 벡터 DB에 저장한다. (기술 선택 근거 문서화)
- [ ]  자연어 질의 → 시맨틱 검색 → LLM 컨텍스트 주입 → 검색에 사용된 문서 출처를 응답에 포함하는 흐름을 구현한다.
- [ ]  유사도 임계값을 설정하여 낮은 품질의 검색 결과가 컨텍스트로 주입되지 않도록 한다.
- [ ]  검색 결과가 없을 때 fallback 응답을 처리한다.
- [ ]  RAG 검색 결과를 바탕으로 Tool Calling을 활용해 실시간 데이터를 조회하여 답변에 포함한다.
- [ ]  Tool 호출 실패 시 RAG 검색 결과만으로 응답하는 fallback을 처리한다.
- 💡 도메인 적용 예시

    <aside>
    🛒

  **커머스: "민감성 피부에 좋은 선크림 추천해줘"**

    ```
    [Tool Calling만 있을 때]
    	→ searchProducts(keyword="민감성 선크림")
    → DB의 LIKE 검색 → 키워드가 정확히 일치하는 것만 반환
    
    [RAG가 추가되면]
    → 질의를 벡터로 변환 → 리뷰·상품 설명 벡터 DB에서 시맨틱 검색
    → "자극 없이 순하다", "아토피 피부에 써봤는데 좋았다" 등 맥락 탐색
    → 해당 상품의 현재 재고·이벤트 실시간 조회 (Tool Calling)
    → "A 선크림을 추천드립니다. 23건의 리뷰에서 민감성 피부 사용자들이
       '자극이 없다'고 평가했습니다. (출처: 상품 #142 리뷰)"
    ```

  핵심: 사용자가 정확한 키워드를 입력하지 않아도 의미가 유사한 데이터를 찾아줍니다.

    </aside>

  **다른 도메인 예시**

    - 숙박: "아이 데리고 가기 좋은 제주 펜션" → 리뷰에서 "키즈풀", "가족 여행" 맥락을 시맨틱 검색
    - 레시피: "냉장고에 닭가슴살이랑 양파가 있는데 뭐 해먹지?" → 재료 조합 기반 시맨틱 검색

### 2. AI 실시간 스트리밍 + 멀티턴 대화

SSE 기반 스트리밍 응답과 멀티턴 대화 히스토리를 구현하고, 토큰 윈도우 관리와 세션 만료 정책으로 비용과 스토리지를 제어한다.

- [ ]  SSE 기반 실시간 스트리밍 응답을 구현한다.
- [ ]  대화 히스토리를 세션 단위로 저장하여 멀티턴 맥락을 유지한다.
- [ ]  최근 N턴만 전달하는 토큰 윈도우 관리로 비용을 제어한다. (N 값 설정 근거 문서화)
- [ ]  세션 만료 정책을 설정하여 스토리지 무한 증가를 방지한다. (예: 마지막 대화로부터 30분)
- [ ]  사용자 간 대화가 격리되는 구조를 보장한다.
- [ ]  대화 세션별 토큰 누적량을 대시보드에서 추적하고 윈도우 크기 조정 근거를 문서화한다.
- 💡 도메인 적용 예시

    <aside>
    🛒

  **스트리밍 체감 차이**

    ```
    [스트리밍 없이]
    사용자 질문 → 3~5초 로딩... → 전체 답변 한 번에 표시
    
    [SSE 스트리밍]
    사용자 질문 → 0.3초 후 첫 글자 → 실시간으로 글자가 나타남
    ```

  **멀티턴 맥락 유지**

    ```
    [1턴] "여름 원피스 추천해줘"
          → "캐주얼한 스타일과 오피스룩 중 어떤 걸 찾으세요?"
    
    [2턴] "캐주얼한 거"          ← 이전 맥락(원피스) 유지
          → "면 소재 캐주얼 원피스 3가지를 추천드릴게요"
    
    [3턴] "두 번째 거 색상 다른 거 있어?"  ← 2턴의 추천 목록 맥락 유지
          → "해당 원피스는 베이지와 네이비도 있습니다."
    ```

  **토큰 윈도우 관리가 필요한 이유**

  대화 1턴당 평균 300토큰이라고 가정하면:

    - 10턴 누적 → 3,000토큰
    - 50턴 누적 → 15,000토큰
    - 100턴 누적 → 30,000토큰

  최근 10턴만 전송하면 어느 시점이든 항상 3,000토큰으로 고정됩니다.

  오래된 대화를 처리하는 전략 3가지:

    - **버리기**: 오래된 턴을 단순 제거 (가장 단순)
    - **요약**: 오래된 대화를 한 문단으로 압축해서 컨텍스트에 유지
    - **메모리 검색**: 현재 질문과 유사한 과거 대화를 벡터 DB에서 꺼내서 주입 (RAG와 동일한 원리를 히스토리에 적용하는 고급 패턴)
    </aside>

### **🗓️ 4주차 : AI 기능 도입**

<aside>
💡

**주요 목표**

</aside>

#### **✅ 필수**

- [ ]  LLM 응답을 JSON 스키마(DTO)에 맞게 구조화하여 파싱 후 DB에 저장

- [ ]  프롬프트 개선 이력 최소 3회 기록 (변경 동기 → 결과 → 다음 개선 방향 형태)
- [ ]  `@Tool`로 백엔드 API 최소 2개 연동, Tool 호출 실패 시 실패 컨텍스트를 LLM에 전달하여 자연어 안내 흐름 구현

#### **🚀 도전**

- [ ]  LLM API 장애(타임아웃·Rate Limit·5xx) 시 Fallback 최소 2가지 구현, 핵심 서비스 정상 동작 보장
- [ ]  환각 방어 최소 1가지 이상 구현 및 문서화
